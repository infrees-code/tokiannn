# MCHOSE 迈从 A7 Pro 鼠标电量监控（Windows 桌面软件）

一个纯原生 Windows 托盘程序，实时监控迈从（MCHOSE）A7 Pro 无线鼠标的电池电量，
低电量时自动弹 Windows 系统通知，支持开机自启动、后台常驻、托盘看电量。

**中文界面 · 无任何第三方依赖 · 免安装 · 使用系统自带编译器即可构建**

> ✅ **2.4G 模式已实测跑通**：A7 Pro 的 2.4G 接收器（VID_5253）**完全不上报标准 HID 电池页**，
> 本软件走的是逆向出来的迈从专属私有协议（特征报告 0x11，XOR 0xFF 混淆），
> 读数与官方软件 MCHOSE HUB 逐字段一致（本机实测 `battery=38%`）。
> 协议来源与验证过程见下文「迈从 A7 Pro 2.4G 私有协议」一节。

## 如何构建（10 秒搞定）

双击 **`构建.bat`** 即可。

脚本使用 Windows **系统自带** 的 C# 编译器（`%WINDIR%\Microsoft.NET\Framework64\v4.0.30319\csc.exe`），
**不需要安装 Visual Studio、.NET SDK 或任何第三方库**。构建成功后会在本目录生成：

```
MCHOSE_A7Pro_BatteryMonitor.exe
```

双击运行即可，Windows 10 / 11 直接可用（系统自带 .NET Framework 4.x 运行时）。

## 排错（运行异常 / 闪退）

### 历史修复记录：启动后几秒内无声消失（原生堆崩溃）

现象：进程启动 2~8 秒后无声退出，日志只有"程序启动/托盘就绪"，没有异常。

Windows 事件日志（`eventvwr.msc` → Windows 日志 → 应用程序）里可见：
`错误应用程序名称: MCHOSE_A7Pro_BatteryMonitor.exe，错误模块名称: ntdll.dll，异常代码: 0xc0000374`。
`0xc0000374` = **STATUS_HEAP_CORRUPTION（堆损坏）**，是 P/Invoke 内存越界写的典型症状。已修复两处：

1. **`HIDP_VALUE_CAPS` 结构体尺寸错误（主因）**
   代码里按 64 字节定义，而 `hidpi.h` 的真实大小是 **72 字节**（漏了 `ReportCount` 之后的
   `USHORT Reserved2[5]`）。于是按 `n*64` 分配缓冲区、`hid.dll` 却写入 `n*72` → 堆溢出。
   同时 `UnitsExp / LogicalMin / LogicalMax / Usage` 全部错位，导致永远读到"0 个电池设备"。
   现已补齐 5 个保留字段，并把缓冲区步长固定为常量 72（不再依赖 `Marshal.SizeOf`），
   启动时还会把实际大小写进日志自检。
2. **重叠 I/O 生命周期错误（次因）**
   原来把托管 `byte[]` 和栈上的 `OVERLAPPED` 直接交给内核做异步 I/O：P/Invoke 只在调用期间
   固定缓冲区，I/O 挂起后 GC 可能移动数组、栈帧也被销毁，内核继续写旧地址 = 堆/栈破坏。
   现改为：缓冲区用 `GCHandle` 显式固定，`OVERLAPPED` 分配到非托管内存，且超时后
   先 `CancelIo` 再用 `bWait=true` 等到内核真正收尾才释放。
3. **顺带加固**：监听 `TaskbarCreated` 消息，资源管理器重启后自动重新注册托盘图标
   （避免出现"进程还在、图标没了"）；每次轮询兜底检查 `Visible`；进程退出写入日志，
   便于区分"正常退出"与"被强杀/原生崩溃"。

> 说明：迈从 A7 Pro 走**专属私有协议**，不受任何开关影响、始终启用；
> 托盘菜单里的「其他品牌接收器探测」（`vendorprobe`，默认关闭）只影响**其他品牌**接收器的通用查询。

程序内置了全局异常捕获与运行日志：

- 日志文件：`%LOCALAPPDATA%\A7ProBatteryMonitor\error.log`
  （资源管理器地址栏粘贴 `%LOCALAPPDATA%\A7ProBatteryMonitor` 回车即可打开）
- 配置文件：同一目录下的 `settings.txt`，其中 `vendorprobe=0` 可关闭厂商协议探测。

判断流程：

1. **启动后右下角一定会出现"鼠标电量监控已启动"的系统通知**——这是程序在运行的证据。
   如果托盘里看不到图标，去**托盘折叠区**（任务栏右下角小箭头）里找。
2. **完全没弹通知，且日志里只有"程序启动"没有"托盘就绪"** → 启动阶段异常，
   日志会记录异常类型和堆栈，把内容发我。
3. **日志干净但进程消失（无任何窗口/弹窗）** → 多半是被安全软件（360/火绒/Defender 等）
   当作"可疑 HID 访问"拦截。处理：
   - 把 exe 加入安全软件白名单；
   - 若日志里出现 `A7 通道不可写` / `A7 应答读取失败：HidD_GetFeature 未返回数据`，
     基本就是被拦截了写入或读取。
4. **重新构建时报错 `error CS0016: 未能写入输出文件…另一个程序正在使用此文件`** →
   说明**旧版本正在运行中**（这正是"程序没闪退"的证据，它只是藏在托盘里）。
   新版 `build.bat` 会自动结束旧进程；若仍失败，右键托盘图标选"退出"后再构建。
5. **电量显示"未检测到设备"** → 先看日志里的 `A7 私有协议读取成功/无应答`：
   成功说明通道正常，只需等下一轮；持续无应答请把 `错误日志` 与 `导出检测报告` 发回。

## 使用说明

1. **启动**：双击 exe，程序进入托盘（任务栏右下角电池小图标），并弹一条"电量监控已启动"的通知。
2. **看电量**：鼠标悬停托盘图标查看精确百分比；双击图标打开主窗口看大字电量 + 电量条。
3. **低电量提醒**：电量 ≤ 阈值（默认 20%）时弹出系统通知；充到阈值 +5% 后重新布防。
4. **开机自启动**：托盘右键 → 勾选"开机自启动"，或主窗口里勾选。
5. **退出**：托盘右键 → 退出。（主窗口点 × 只是隐藏到托盘）

配置保存在 `%LOCALAPPDATA%\A7ProBatteryMonitor\settings.txt`（`interval` 为轮询秒数，默认 300）。

## 技术原理与兼容性说明（请务必阅读）

### 电量读取：三层兼容策略（2.4G 模式已实测跑通）

Windows 不提供"无线鼠标电量"的统一 API，2.4G 接收器尤其常用私有协议。本软件按优先级依次尝试三条通道：

1. **标准 HID 电池用法页**（Generic Device Controls 0x06/0x20，或 Battery System 0x20/0x01）
   —— Input / Feature 双通道读取。蓝牙模式下命中率极高；部分 2.4G 接收器也会以这种方式上报。
2. **迈从 A7 Pro 专属私有协议（VID_5253，2.4G 接收器的唯一可行通道）**
   —— 见下一节。**本机 A7 Pro 的 2.4G 接收器完全不上报标准电池页，只能走这条。**
3. **其他品牌接收器的通用探测**（17 字节命令：report ID 0x08 + 命令 0x04 + 校验和 0x55，
   Pulsar / Kysona / VXE / ATK 同族）—— 默认关闭，托盘菜单「其他品牌接收器探测」可开启。

---

### 迈从 A7 Pro 2.4G 私有协议（已逆向完成并逐字段验证）

**结论：读取成功，且与官方软件 MCHOSE HUB 的读数逐字段一致。**

协议来源是**权威定义而非猜测**——从 MCHOSE HUB 自己的前端 bundle 中直接提取
（Chromium 磁盘缓存 `%APPDATA%\MCHOSEHUB\Cache\Cache_Data\f_000011` 内的明文代码）：

```js
// 命令表
NM = { "0x11 0x06": { order: `11 06 ${"00 ".repeat(19).trim()}`, parser: vXe }, ... }

// 应答解析器：小端
vXe = uint16("vid"), uint16("pid"), uint32("fwVersion"),
      bit3("connectMode"), bit1("connectStatus"), bit4("inReserved"),
      uint8("batteryLevel"), uint8("chargeStatus")

// 收发逻辑（gP）
await device.sendFeatureReport(0x11, order.slice(3).split(" ").map(d => ("0x"+d) ^ 255));
const r = await device.receiveFeatureReport(0x11);
const data = xor255(r.slice(2));      // 丢掉 [报告ID] + [命令回显]
return vXe.parse(data);
```

即：**命令与应答整帧按 XOR 0xFF 混淆；特征报告 0x11 是一个"邮箱"——写入命令、回读应答。**
命令字节为 `11 06 00 00 … 00`（19 个 0x00），其中 `0x11` 同时是特征报告 ID。

**本机实测应答（HID 原始字节）：**

```
53 52 10 00 | 04 05 07 00 | 09 | 26 | 00
└ vid=0x5253 └ pid=0x0010 └ fw=460036 └ 位域 └ 电量=0x26=38% └ 充电=0
```

**与官方软件的交叉验证**（MCHOSE HUB 写入的 `localStorage` → `deviceInfoMap`）：

```json
{"MCHOSE A7 Pro":{"vid":21075,"pid":16,"fwVersion":460036,"connectMode":1,
                  "connectStatus":1,"inReserved":0,"batteryLevel":38,"chargeStatus":0}}
```

vid / pid / fwVersion / connectMode / connectStatus / batteryLevel / chargeStatus **全部一致**。
（该键的历史值里还能看到 59 → 31 → 98 → 30 → **40** → 38 的连续记录，40 即用户当时
在 HUB 界面看到的读数。设备表里的 `pids:["16","4129","4128"]` 也解释了
为何 USB 描述符 PID 是 4129(0x1021) 而报文里是 16(0x0010)。）

位域字节 `0x09` 按**低位优先**拆分才自洽（HUB 的取值也印证了这一点）：
`connectMode = bits & 0x07 = 1`（1 = 2.4G）、`connectStatus = (bits>>3)&1 = 1`（在线）、
`inReserved = bits>>4 = 0`。

#### 实现中踩到的两个坑（都已固化在代码里，改动前务必阅读）

1. **必须先"预热读"邮箱再发命令。**
   特征报告 0x11 保存着上一次命令的应答。若直接写入新命令，实测会退化成
   "只回显刚写入的内容"，连续读 1.5 秒也拿不到真实应答（Python 与 C# 均复现）。
   先空读 1~2 次把残留消费掉，再下发命令，即可稳定拿到新应答。
2. **回读缓冲区长度必须取 `FeatureReportByteLength`（本机 65），不能用命令自身长度 21。**
   用 21 去读同样只会拿到回显。
   另外，为了彻底排除陈旧帧，解码时还要求**应答帧第 2 字节（命令回显）等于 0x06**，
   并校验 `vid == 0x5253`、`pid ∈ {0x1021, 0x0010}`、电量 ≤ 100，任一不符即丢弃重试。

> 探明的设备拓扑（VID_5253 PID_1021 复合设备，共 5 个 HID 集合）：
> `mi_00` 鼠标（X/Y/滚轮，无电池用法，非管理员打不开）、`mi_01` 键盘 + 多媒体、
> **`mi_02&col02`（usagePage 0xFF01，特征报告 0x11/0x12/0x14）= 命令/应答通道**、
> `mi_02&col01`（usagePage 0xFF0B，报告 0x2A/0x2B/0x2C/0x2D）= 另一条厂商通道，
> 但向它写特征报告会失败（err=1），不用于取电量。
> 输入中断管道上还会周期性推送 XOR 混淆帧：`E5 06 …`（命令 ACK）与
> `E2 01 01 00 26 … "A7 Pro"`（状态推送，其 byte[4] 同样是电量 38%），可作旁证。

### 诚实披露：什么情况下会显示"未检测到"？

- **迈从接收器偶发无应答**：该邮箱通道偶尔会被占用（例如官方 HUB 正在运行时）或设备短暂休眠。
  软件会自动重试 **3 轮 × 8 次**；若仍失败，会**沿用最近 10 分钟内的成功读数**并在托盘标注"（上次读数）"，
  不会在"电量"与"未检测到设备"之间乱跳。
- **其他品牌 2.4G 接收器**：协议各不相同，第 1、3 通道未命中时请用"导出检测报告"反馈，
  适配后即可支持。
- **蓝牙模式通常能直接读到**：如果 2.4G 暂时读不到又急着用，可临时切蓝牙模式验证软件工作正常。
- **有线充电中**：识别到充电标志时会显示"充电中"且不触发低电量弹窗。

### 关键实现点（给想改代码的你）

- **设备枚举**：`SetupDiGetClassDevs(HID GUID)` → `SetupDiEnumDeviceInterfaces` →
  `SetupDiGetDeviceInterfaceDetail`（注意 64 位系统 detail 结构 cbSize=8 的经典大坑，代码已处理）。
- **电池能力识别**：`HidP_GetValueCaps` 按 `HIDP_VALUE_CAPS`（与 hidpi.h 逐字节对齐，**72 字节**）扫描，
  命中 `(0x06,0x20)` 或 `(0x20,0x01)` 即认定为电池值。
- **读数**：先 GET_REPORT(Input)（`HidD_GetInputReport`），失败再 GET_REPORT(Feature)（`HidD_GetFeature`），
  用 `HidP_GetUsageValue` 从报告中解析；量程非 0~100 的设备按逻辑最大值线性换算。
- **迈从专属协议**：见上文「迈从 A7 Pro 2.4G 私有协议」一节，核心是
  "预热读邮箱 → 写 `11 06` 命令 → 回读 0x11 特征报告 → XOR-FF 解码 + vid/命令回显双重校验"。
- **设备匹配**：名称含 `A7` / `MCHOSE` / `迈从` 的设备优先；否则取第一个可读数的电池设备。
- **通知防骚扰**：只在"由高转低"那一刻弹一次，回充到阈值+5% 后才重新布防。
- **托盘图标**：16×16 位图实时绘制电池外形 + 按电量比例填充 + 三段变色，旧 GDI 句柄用 `DestroyIcon` 释放防泄漏。
